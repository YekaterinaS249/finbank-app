# Спецификация модуля «Регистрация» (FinBank)

Основано на текущей реализации: `AuthWebController`, `AuthApiController`,
`AuthService`, `RegisterRequest`.

**v2 — что изменилось по сравнению с первой версией:** требования
пронумерованы и получили приоритет, обычный текстовый список граничных
случаев превращён в таблицу тест-кейсов (ID / шаги / ожидаемый результат /
приоритет), добавлена трассировка «требование → тест-кейсы», отдельно
выделены баги-кандидаты и открытые вопросы, которые нужно решить до
написания тестов.

## 1. Назначение

Позволяет новому пользователю создать учётную запись в FinBank. При успешной
регистрации автоматически открывается один текущий (CHECKING) счёт в USD с
начальным балансом **1000.00**.

## 2. Точки входа

| Канал | Путь | Метод |
|---|---|---|
| UI | `/register` | `GET` — форма, `POST` — отправка |
| API | `/api/auth/register` | `POST` |

## 3. Входные данные

| Поле | Тип | Обязательное | Правила валидации | Где проверяется |
|---|---|---|---|---|
| `fullName` | string | да | не пустое (`@NotBlank`) — пробелы по краям **не** обрезаются, ограничения по длине/символам **нет** | сервер |
| `email` | string | да | не пустое + формат email (`@Email`, Hibernate Validator) | сервер |
| `password` | string | да | не пустое, **минимум 8 символов**; максимума, требований к сложности (цифры/спецсимволы/регистр) — нет | сервер |

На UI-форме нет JS-валидации на клиенте — все проверки происходят на
сервере после сабмита (обычный `POST`, без AJAX).

## 4. Функциональные требования

| ID | Требование | Приоритет |
|---|---|---|
| REQ-REG-01 | Email уникален без учёта регистра (`existsByEmailIgnoreCase`) | Must |
| REQ-REG-02 | Email приводится к нижнему регистру перед сохранением | Must |
| REQ-REG-03 | Пароль хранится только как BCrypt-хэш, нигде не логируется в открытом виде | Must |
| REQ-REG-04 | При успешной регистрации создаётся ровно 1 счёт: CHECKING, USD, баланс 1000.00 | Must |
| REQ-REG-05 | Номер счёта генерируется автоматически (`FB` + 10 цифр) и уникален | Must |
| REQ-REG-06 | Успешная регистрация через UI не логинит пользователя автоматически — требуется отдельный вход | Must (текущее поведение) |
| REQ-REG-07 | Успешная регистрация через API сразу возвращает годный JWT | Must (текущее поведение) |
| REQ-REG-08 | Согласие на условия использования / чекбокс — не требуется (не реализовано) | Out of scope |
| REQ-REG-09 | Подтверждение email — не требуется (не реализовано) | Out of scope |
| REQ-REG-10 | Captcha / rate limiting на регистрацию — не реализовано | Out of scope |

## 5. Успешный сценарий

**UI:**
1. Пользователь открывает `/register`, заполняет форму, жмёт «Register».
2. Сервер создаёт пользователя и счёт.
3. Редирект на `/login?registered` — на странице логина показывается баннер
   об успешной регистрации (`data-testid="registered-banner"`).
4. JWT/сессия при этом **не выдаются** — после регистрации нужно отдельно
   залогиниться (см. REQ-REG-06).

**API:**
1. `POST /api/auth/register` с телом:
   ```json
   { "fullName": "Jane Doe", "email": "jane@example.com", "password": "P@ssw0rd123" }
   ```
2. Ответ `201 Created`:
   ```json
   { "token": "<jwt>", "tokenType": "Bearer", "expiresInSeconds": 1800, "email": "jane@example.com" }
   ```
   Токен уже готов к использованию (см. REQ-REG-07).

## 6. Ошибки

| Ситуация | UI-поведение | API-поведение |
|---|---|---|
| Email уже занят | Форма перерисовывается, баннер `data-testid="register-error"` с текстом `An account with email '<email>' already exists` | `409 Conflict`, тело `ApiError` с тем же текстом в `messages` |
| Пустое/невалидное поле | Форма перерисовывается, ошибка под конкретным полем (`fullname-error` / `email-error` / `password-error`) | `400 Bad Request`, `ApiError.messages` — список вида `"email: Email must be a valid address"` |
| Пароль короче 8 символов | Ошибка под полем password: `Password must be at least 8 characters long` | то же сообщение в `messages` |
| Невалидный JSON / отсутствует Content-Type | — | `400 Bad Request` (стандартная обработка Spring) |

Формат `ApiError`:
```json
{
  "timestamp": "2026-08-19T20:30:00Z",
  "status": 409,
  "error": "Conflict",
  "messages": ["An account with email 'jane@example.com' already exists"],
  "path": "/api/auth/register"
}
```

## 7. Тест-кейсы (граничные и негативные случаи)

| ID | Заголовок | Шаги | Ожидаемый результат | Приоритет |
|---|---|---|---|---|
| TC-REG-01 | Email отличается только регистром от существующего | 1. Зарегистрировать `jane@test.com`. 2. Зарегистрировать `Jane@Test.com` | Второй запрос отклонён как дубликат (409 / баннер ошибки) | High |
| TC-REG-02 | Email с пробелами по краям | Отправить email `" jane@test.com "` | ⚠️ Открытый вопрос — см. раздел 9. Сейчас пробелы не обрезаются | High |
| TC-REG-03 | Очень длинное значение fullName | Отправить `fullName` из 5000 символов | Не должно быть 500-й ошибки; поведение системы задокументировать по факту | Medium |
| TC-REG-04 | Невалидный формат email | Отправить `not-an-email`, `test@`, `test@@test.com` | 400 / ошибка валидации под полем email | High |
| TC-REG-05 | Пароль на границе — 8 символов | Отправить пароль ровно из 8 символов | Регистрация проходит успешно | High |
| TC-REG-06 | Пароль на границе — 7 символов | Отправить пароль из 7 символов | 400 / ошибка `Password must be at least 8 characters long` | High |
| TC-REG-07 | Двойная отправка формы (race condition) | Отправить два одинаковых запроса регистрации почти одновременно | Ровно один пользователь создан; второй запрос получает понятную 4xx-ошибку, а не 500 и не дубликат | High |
| TC-REG-08 | XSS в fullName | `fullName = "<script>alert(1)</script>"` | Значение должно быть экранировано при выводе на дашборде (`Welcome, ...`), скрипт не должен исполниться | High |
| TC-REG-09 | Регистрация без тела запроса (API) | `POST /api/auth/register` без JSON-тела | 400 Bad Request | Medium |
| TC-REG-10 | Лишние поля в JSON (API) | Добавить `"role": "ADMIN"` в тело запроса | Поле игнорируется, пользователь создаётся с обычными правами (нет привилегированных полей в DTO) | Medium |
| TC-REG-11 | Пустая строка вместо email/пароля/имени | Отправить `""` в каждое поле по очереди | 400 / ошибка `must not be blank` под соответствующим полем | High |
| TC-REG-12 | Проверка автосоздания счёта | Зарегистрировать нового пользователя, залогиниться, открыть дашборд | Ровно 1 счёт: тип CHECKING, валюта USD, баланс 1000.00 | Must / High |
| TC-REG-13 | Уникальность номера счёта | Зарегистрировать 2+ пользователей подряд | Номера счетов у всех разные | Medium |

## 9. Открытые вопросы (нужно решить до написания тестов)

1. **Пробелы в email/пароле.** Сейчас не обрезаются (`trim()` не
   вызывается). Это ожидаемое поведение или баг, который нужно завести и
   потом переисследовать? От ответа зависит ожидаемый результат TC-REG-02.
2. **Максимальная длина `fullName`.** Ограничения нет ни на UI, ни в БД
   (`String` без `@Size`/`@Column(length=...)`) — это осознанное решение
   или недосмотр?
3. **Требования к сложности пароля.** Сейчас достаточно 8 любых символов
   (например, `"aaaaaaaa"` пройдёт). Для fintech это низкая планка — нужно
   ли фиксировать более строгую политику как отдельное требование?
4. **Race condition на уникальность email.** На уровне БД есть
   `UNIQUE`-констрейнт на `email`, значит один из двух параллельных
   запросов должен упасть — но нужно проверить (TC-REG-07), что ошибка
   приходит клиенту как аккуратный `4xx`/`409`, а не как `500` с трассировкой
   стека.

## 10. Баги-кандидаты (предварительно, требуют подтверждения тестами)

- Отсутствие `trim()` для email/пароля/имени (см. открытый вопрос №1).
- Отсутствие верхней границы длины `fullName` может допускать чрезмерно
  большие запросы (потенциальная DoS-поверхность, TC-REG-03).
- Race condition при двойном сабмите формы регистрации (TC-REG-07) — не
  подтверждено, но стоит проверить в первую очередь.
