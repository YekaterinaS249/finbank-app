# Password Requirements — Acceptance Criteria (Given/When/Then)

Обновлённая политика пароля для регистрации FinBank. **Эта версия
заменяет** правила пароля из `Registration-Field-Validation-Rules.md`
(там было: 12–64 символа, обязательна буква и цифра) — ниже зафиксированы
новые числа и явно отменено требование к составу символов.

## ⚠️ Влияние на уже реализованный код

В прошлый раз я реализовала `RegistrationValidator` под старые правила
(`PASSWORD_MIN_LENGTH = 12`, `PASSWORD_MAX_LENGTH = 64`, обязательны
`PASSWORD_MISSING_LETTER` / `PASSWORD_MISSING_DIGIT`) и хэширование через
`BCryptPasswordEncoder`. Этот документ им противоречит по пунктам 1–3 и 7
(новые границы 15/128, отмена требования буква+цифра, рекомендация
Argon2id вместо BCrypt). Реализация пока **не изменена** — только
Acceptance Criteria ниже. Скажи, если нужно сразу привести код в
соответствие.

---

## Сводка правил (для справки)

| # | Правило | Значение |
|---|---|---|
| 1 | Минимальная длина | 15 символов |
| 2 | Максимальная длина | 128 символов, без молчаливого обрезания |
| 3 | Требования к составу | НЕТ обязательных категорий символов (uppercase/lowercase/digit/special не требуются) |
| 4 | Регистрозависимость | `MySecurePassword` ≠ `mysecurepassword` |
| 5 | Confirm Password | точное совпадение, иначе ошибка `Пароли не совпадают.` |
| 6 | Copy/Paste, autofill, password manager | не блокируются |
| 7 | Хранение | только хэш (рекомендуется Argon2id), plaintext нигде не хранится |

Явно исключено из этой спецификации (не реализовывать, не тестировать как
требование): проверка по списку распространённых/скомпрометированных
паролей, отдельные правила для Unicode, отдельные правила для пробелов,
индикатор сложности пароля, brute-force protection, rate limiting для
password-эндпоинтов, любые другие правила, не перечисленные выше.

## AC-PWD-01 — Минимальная длина

**AC-PWD-01a (negative, boundary): 14 символов — невалидно**
```
Given  пользователь находится на форме регистрации
When   он вводит пароль длиной ровно 14 символов (например, "Abcdefghijklmn")
       и такое же значение в Confirm Password
       и отправляет форму
Then   регистрация не завершается успешно
       и возвращается ошибка с кодом PASSWORD_TOO_SHORT
       и текст ошибки сообщает о минимальной длине в 15 символов
       и пользователь не создаётся в базе данных
```

**AC-PWD-01b (positive, boundary): 15 символов — валидно**
```
Given  пользователь находится на форме регистрации
When   он вводит пароль длиной ровно 15 символов (например, "Abcdefghijklmno")
       и такое же значение в Confirm Password
       и все остальные поля формы валидны
       и отправляет форму
Then   регистрация завершается успешно (нет ошибки PASSWORD_TOO_SHORT)
       и пользователь создаётся в базе данных
```

## AC-PWD-02 — Максимальная длина

**AC-PWD-02a (positive, boundary): 128 символов — валидно**
```
Given  пользователь находится на форме регистрации
When   он вводит пароль длиной ровно 128 символов
       и такое же значение в Confirm Password
       и все остальные поля формы валидны
       и отправляет форму
Then   регистрация завершается успешно (нет ошибки PASSWORD_TOO_LONG)
       и пользователь создаётся в базе данных
```

**AC-PWD-02b (negative, boundary): 129 символов — невалидно**
```
Given  пользователь находится на форме регистрации
When   он вводит пароль длиной ровно 129 символов
       и такое же значение в Confirm Password
       и отправляет форму
Then   регистрация не завершается успешно
       и возвращается ошибка с кодом PASSWORD_TOO_LONG
       и пользователь не создаётся в базе данных
```

**AC-PWD-02c (negative): пароль не обрезается молча**
```
Given  пользователь вводит пароль длиной 129+ символов
When   форма отправлена и получена ошибка PASSWORD_TOO_LONG
Then   система не должна была сохранить усечённую до 128 символов версию
       пароля — запрос отклоняется целиком, пользователь не создаётся
       (проверяется тем, что после этой попытки в БД нет записи с данным
       email/телефоном вообще)
```

## AC-PWD-03 — Отсутствие требований к составу символов

**AC-PWD-03a (positive): пароль без заглавных букв — валиден**
```
Given  пользователь вводит пароль из 15+ символов, полностью в нижнем
       регистре, без цифр и спецсимволов (например, "onlylowercaseletters")
When   он подтверждает тем же значением в Confirm Password и отправляет форму
Then   регистрация завершается успешно
       и ошибка, связанная с отсутствием заглавной буквы, НЕ возвращается
       (в системе в принципе не существует кода ошибки для этого правила)
```

**AC-PWD-03b (positive): пароль без строчных букв — валиден**
```
Given  пользователь вводит пароль из 15+ символов, полностью в верхнем
       регистре (например, "ONLYUPPERCASELETTERS")
When   он подтверждает тем же значением в Confirm Password и отправляет форму
Then   регистрация завершается успешно
```

**AC-PWD-03c (positive): пароль без цифр — валиден**
```
Given  пользователь вводит пароль из 15+ букв без единой цифры
       (например, "PasswordNoDigitsHere")
When   он подтверждает тем же значением в Confirm Password и отправляет форму
Then   регистрация завершается успешно
```

**AC-PWD-03d (positive): пароль без спецсимволов — валиден**
```
Given  пользователь вводит пароль из 15+ букв и цифр без единого
       спецсимвола (например, "Password12345678")
When   он подтверждает тем же значением в Confirm Password и отправляет форму
Then   регистрация завершается успешно
```

**AC-PWD-03e (positive): пароль только из строчных букв (пример из ТЗ)**
```
Given  пользователь вводит пароль, состоящий исключительно из строчных
       букв, длиной ≥15 символов (например, "abcdefghijklmno")
When   он подтверждает тем же значением в Confirm Password и отправляет форму
Then   регистрация завершается успешно — длины достаточно, состав
       символов не проверяется
```

## AC-PWD-04 — Регистрозависимость

**AC-PWD-04a (positive): регистрация с конкретным регистром**
```
Given  пользователь регистрируется с паролем "MySecurePassword123456"
When   регистрация завершена успешно
Then   в базе данных сохранён хэш именно от строки "MySecurePassword123456"
       с сохранением регистра каждого символа (хэш не приводится к
       верхнему/нижнему регистру перед хэшированием)
```

**AC-PWD-04b (negative): логин с другим регистром пароля отклоняется**
```
Given  пользователь зарегистрирован с паролем "MySecurePassword123456"
When   он пытается войти с паролем "mysecurepassword123456"
       (тот же набор символов, другой регистр)
Then   логин завершается ошибкой "неверные учётные данные"
       (пароли считаются разными строками)
```

**AC-PWD-04c (positive): логин с точно тем же регистром проходит**
```
Given  пользователь зарегистрирован с паролем "MySecurePassword123456"
When   он вводит на логине точно "MySecurePassword123456"
Then   логин завершается успешно
```

## AC-PWD-05 — Подтверждение пароля (Confirm Password)

**AC-PWD-05a (positive): пароли совпадают**
```
Given  пользователь вводит в поле Password значение "CorrectPassword1234567"
When   он вводит точно такое же значение в поле Confirm Password
       и отправляет форму (остальные поля валидны)
Then   регистрация завершается успешно
       и ошибка PASSWORD_MISMATCH не возвращается
```

**AC-PWD-05b (negative): пароли не совпадают**
```
Given  пользователь вводит в поле Password значение "CorrectPassword1234567"
When   он вводит в поле Confirm Password другое значение,
       например "DifferentPassword123456"
       и отправляет форму
Then   регистрация не завершается успешно
       и возвращается ошибка с кодом PASSWORD_MISMATCH
       и текст ошибки, показываемый пользователю: "Пароли не совпадают."
       и пользователь не создаётся в базе данных
```

**AC-PWD-05c (negative, boundary): совпадение по длине, но не по регистру**
```
Given  пользователь вводит в поле Password значение "SecurePassword1234567"
When   он вводит в Confirm Password то же значение, но с одним символом в
       другом регистре — "securePassword1234567"
       и отправляет форму
Then   значения считаются несовпадающими (сравнение регистрозависимое,
       см. AC-PWD-04)
       и возвращается ошибка PASSWORD_MISMATCH с текстом "Пароли не совпадают."
```

**AC-PWD-05d (negative): пустое Confirm Password**
```
Given  пользователь заполнил поле Password валидным значением
When   поле Confirm Password оставлено пустым и форма отправлена
Then   регистрация не завершается успешно
       и возвращается ошибка CONFIRM_PASSWORD_REQUIRED
       (отдельно от PASSWORD_MISMATCH — поле не заполнено, а не "не совпало")
```

## AC-PWD-06 — Copy/Paste, Autofill, Password Manager

**AC-PWD-06a (positive, UI): вставка пароля через Copy/Paste разрешена**
```
Given  пользователь скопировал валидный пароль (15–128 символов) в буфер
       обмена
When   он вставляет его в поле Password сочетанием клавиш / контекстным
       меню "Вставить" (Ctrl+V / Cmd+V)
Then   значение поля Password корректно заполняется вставленным паролем
       (не блокируется JS-обработчиком paste-события, атрибут поля не
       содержит autocomplete="off" или иных блокировок вставки)
```

**AC-PWD-06b (positive, UI): вставка в Confirm Password разрешена**
```
Given  пользователь скопировал тот же пароль в буфер обмена
When   он вставляет его в поле Confirm Password
Then   значение корректно вставляется, поле не блокирует paste
       и, при совпадении с Password, форма проходит валидацию совпадения
```

**AC-PWD-06c (positive, UI): autofill браузера/password-менеджера разрешён**
```
Given  в браузере/password-менеджере сохранены учётные данные для домена
       FinBank
When   пользователь открывает форму регистрации/логина
Then   браузер/менеджер может предложить автозаполнение полей email и
       password (поля не имеют autocomplete="off"/"new-password"-блокировок,
       препятствующих штатному autofill; для формы регистрации поле
       password должно иметь autocomplete="new-password", а не блокировку
       автозаполнения в принципе)
```

**AC-PWD-06d (negative — то, чего быть НЕ должно): JS не должен слушать paste/keydown для блокировки**
```
Given  форма регистрации открыта в браузере
When   выполняется попытка вставить значение в поле Password
       программным событием paste
Then   событие paste не должно быть отменено (event.preventDefault()
       не вызывается на paste для полей password/confirmPassword)
```

## AC-PWD-07 — Хранение пароля (хэширование, без plaintext)

**AC-PWD-07a (positive): в БД хранится хэш, не исходный пароль**
```
Given  пользователь успешно зарегистрирован с паролем "SomePlainPassword123456"
When   выполняется прямой SQL-запрос к таблице пользователей
       (SELECT password_hash FROM users WHERE email = ...)
Then   значение в столбце password_hash НЕ равно "SomePlainPassword123456"
       и не содержит эту строку как подстроку
       и по формату соответствует Argon2id-хэшу (префикс "$argon2id$...")
```

**AC-PWD-07b (positive): исходный пароль нигде не встречается в БД**
```
Given  пользователь успешно зарегистрирован с уникальным, специально
       сгенерированным для теста паролем (например, "Uniq3TestMarkerPwd987")
When   выполняется полнотекстовый поиск этой строки по всем столбцам
       таблицы users (и, если применимо, по audit_logs)
Then   исходная строка пароля не найдена ни в одной записи БД
```

**AC-PWD-07c (positive): пароль не логируется в открытом виде**
```
Given  пользователь регистрируется или пытается залогиниться (успешно или
       неуспешно) с известным паролем
When   просматриваются логи приложения за это время
Then   значение пароля в открытом виде не встречается ни в одной строке
       лога (ни в успешном, ни в неуспешном сценарии, включая логи ошибок
       валидации)
```

**AC-PWD-07d (positive): пароль не возвращается в API-ответах**
```
Given  выполнен запрос POST /api/auth/register или GET /api/users/me
When   получен ответ сервера
Then   тело ответа не содержит ни значения password, ни confirmPassword,
       ни password_hash ни в каком виде (ни в открытом, ни в хэшированном)
```

**AC-PWD-07e (positive): один и тот же пароль у двух пользователей даёт разные хэши (соль)**
```
Given  два разных пользователя регистрируются с одинаковым паролем
       "SamePassword1234567" каждый
When   выполняется сравнение значений password_hash обеих записей в БД
Then   хэши различаются между собой (используется случайная соль на
       каждую запись — что и Argon2id, и BCrypt делают по умолчанию)
```
