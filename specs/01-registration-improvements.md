# Регистрация — предложения по улучшению спецификации (с примерами)

Ниже — конкретные предложения по каждому слабому месту из открытых
вопросов и багов-кандидатов v2, с примерами «было / стало», чтобы было
видно, что именно поменяется в поведении.

## 1. Обрезка пробелов (trim) для email и имени

**Сейчас:**
```
Ввод:    email = "  jane@test.com  "
Сохранено в БД: "  jane@test.com  "
Результат: пользователь регистрируется с пробелами в email
```
Проблема: при логине пользователь введёт `jane@test.com` (без пробелов) —
и если сравнение точное, а не через `trim`, вход не пройдёт, хотя это тот
же самый email визуально.

**Предлагаемое улучшение:** обрезать пробелы по краям для `email` и
`fullName` перед валидацией и сохранением.
```
Ввод:    email = "  jane@test.com  "
Сохранено в БД: "jane@test.com"
```
Новое требование: **REQ-REG-02a** — `email` и `fullName` обрезаются
(`trim()`) до валидации.
Новый тест-кейс: **TC-REG-02** (обновлён) — регистрация с пробелами
→ email сохранён без пробелов → логин тем же email без пробелов проходит
успешно.

## 2. Политика сложности пароля

**Сейчас:**
```
Пароль "aaaaaaaa" (8 одинаковых букв) — проходит валидацию
```
Для fintech-продукта это слабая планка: пароль от банковского счёта не
должен приниматься, если легко подбирается.

**Предлагаемое улучшение:** минимум 8 символов **плюс** минимум одна
цифра и одна буква (можно ужесточить дальше — заглавная буква,
спецсимвол — по решению продукта).
```
Отклонить:  "aaaaaaaa"          → "Password must contain at least one digit"
Отклонить:  "12345678"          → "Password must contain at least one letter"
Принять:    "passw0rd"          → OK
Принять:    "P@ssw0rd123"       → OK
```
Новое требование: **REQ-REG-11** — пароль должен содержать минимум одну
букву и одну цифру (Should, не Must — требует согласования с продуктом).
Новые тест-кейсы:
- TC-REG-14 — пароль из одних цифр отклонён
- TC-REG-15 — пароль из одних букв отклонён
- TC-REG-16 — пароль с буквой и цифрой на границе (8 символов) принят

## 3. Верхняя граница длины `fullName`

**Сейчас:**
```
fullName = "A" * 5000  → неизвестное поведение (не описано, не ограничено)
```

**Предлагаемое улучшение:** ограничить разумным максимумом, например
120 символов (стандартно для ФИО с запасом), с понятной ошибкой.
```
fullName = "A" * 121  → 400, "fullName: size must be between 1 and 120"
fullName = "Jane Doe" → OK
```
Новое требование: **REQ-REG-12** — `fullName` от 1 до 120 символов.
Тест-кейс TC-REG-03 (обновлён): граница 120/121 символ вместо абстрактных
«5000 символов».

## 4. Race condition при двойной отправке формы

**Сейчас:** поведение не проверено; в худшем случае — 500-ошибка вместо
понятного ответа при двух одновременных запросах с одним email.

**Предлагаемое улучшение:** явно описать ожидаемый контракт —
```
Запрос A: POST /api/auth/register {email: "race@test.com", ...}  → 201, ровно один раз
Запрос B: тот же email, отправлен в это же мгновение              → 409 Conflict
                                                                       (НЕ 500, НЕ дубликат в БД)
```
Новое требование: **REQ-REG-13** — при конкурентной регистрации одного и
того же email ровно один запрос успешен (201), остальные получают 409, без
исключений уровня 500 в ответе клиенту.
Это уже сформулированный тест-кейс TC-REG-07 — просто теперь у него есть
точный ожидаемый HTTP-контракт, а не общая формулировка «понятная ошибка».

## 5. Единообразие сообщений об ошибках между UI и API

**Сейчас:** UI показывает текст ошибки в баннере, API — в `messages[]`
внутри `ApiError`. Тексты совпадают для бизнес-ошибок (например, дубликат
email), но для *валидационных* ошибок форматы разные:
```
UI:  "Password must be at least 8 characters long"          (под полем)
API: "password: Password must be at least 8 characters long" (с префиксом имени поля)
```
**Предлагаемое улучшение:** зафиксировать это явно как **ожидаемое
расхождение**, а не оставлять как случайное наблюдение — чтобы при
написании тестов не тратить время на выяснение, баг это или нет.
Новое требование: **REQ-REG-14** — префикс `"<fieldName>: "` в
сообщении — часть контракта API-ошибок, в UI он не отображается.

## 6. XSS в имени — явный ожидаемый результат вместо общего "должно быть экранировано"

**Сейчас формулировка:** «скрипт не должен исполниться» — расплывчато для
теста.

**Предлагаемое улучшение:** дать точный ожидаемый HTML на выходе.
```
Ввод:  fullName = "<script>alert(1)</script>"
Ожидаемый рендер на дашборде (просмотр исходного кода страницы):
  Welcome, &lt;script&gt;alert(1)&lt;/script&gt;
Не должно быть:
  Welcome, <script>alert(1)</script>   (т.е. неэкранированный тег)
```
Тест-кейс TC-REG-08 (обновлён) — конкретизирован ожидаемый HTML вместо
общей фразы.

## 7. Rate limiting / anti-abuse (сейчас полностью отсутствует)

**Сейчас:** можно зарегистрировать неограниченное число аккаунтов подряд с
одного IP за секунды.

**Предлагаемое улучшение (как будущее требование, не для текущей версии
приложения — фиксируем как техдолг):**
```
Пример правила: не более 5 регистраций с одного IP за 10 минут
6-й запрос за период → 429 Too Many Requests
```
Помечаем как **Won't fix в текущей версии**, но фиксируем в спецификации,
чтобы это не терялось и не считалось «пропущенным» багом при аудите.
